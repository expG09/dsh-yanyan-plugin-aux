# 设计取舍

一页纸，记几个当时想清楚的问题。以后要改它的人（包括几个月后的我）先看这里。

## 为什么不做成改 DSH

插件是 profile 下的独立包，靠 `cordis.patch.yml` 插一行挂上去，DSH 本体和任何 `node_modules` 都不动。卸载 = 删一行 + 删目录。

代价是只能站在公开的接缝上：`agent/pre-step` 事件、`ctx.tokenMeter` 服务。接缝不够用的时候，是收窄需求，不是去 patch 内部。

## 为什么挂在 pre-step 注入

宿主每轮发请求前会走一次 `agent/pre-step`，处理函数能拿到 `decision.messages`，往里追加消息即可让这条内容进入本轮请求。`@deepseek-ai/dsh-time-context` 就是这么做时钟读数的，照抄它的形状：

- 用 `createUserMessage` 构造，`source.kind` 写插件自己的名字，`form: 'snapshot'` 加 `sections`，这样消息在会话日志里可回溯、也能被审计出是谁注的；
- 监听器用 `{ prepend: true }`，排在别的 pre-step 监听器前面。

反面选项是不注入、只提供工具。没选它，是因为工具要我主动想起去调，而水位恰恰是「想不起来看」的时候最需要。

## 为什么读不到就静默

`contextPressure()` 的 `pressureTokens` 和 `contextWindow` 都可能缺：宿主刚起来、这一场还没发过请求、或者换了模型没拿到容量。这时：

- 不注入任何内容（注入一条「水位未知」只会占位置）；
- 不抛错、不写日志刷屏（水位是辅助信息，不该有能力打断会话）。

同样的原则用在时钟写上：写文件失败就吞掉，不让它影响聊天。

## 为什么阈值每会话只记一次

50/70 是「该做点什么了」的信号，不是仪表盘。每轮重复提醒会变成噪音，反而让人学会忽略它。所以内存里按会话记已提醒的坎，跨过才算一次；插件重启后重计，接受这个不精确。

## 为什么累计和百分比分开看

百分比是当前窗口占用，折叠之后会回落；累计 token 只增不减。拿累计反推百分比在折叠前勉强成立，折叠后必然失真。

所以：**该不该换新会话看累计**（那是总账），**离下次压缩还有多远看百分比**（那个由宿主自己管）。插件只负责把百分比送到模型眼前，不试图把两个概念缝成一个。

## 时钟行为什么要带百分比

同一行里既有真实时间又有当时的水位，事后回看能对上「几点开始变慢」这类问题。多写几个字符，省一次交叉比对。

## 为什么设置单独落一个文件

`cordis.patch.yml` 是用户 profile 的东西，里面还有别的插件的行、注释和 `!!js` 表达式。
插件不该为了存自己的四个开关去重写它。所以：

- 设置页把值写到 `%USERPROFILE%\.dsh\aux-settings.json`，只碰自己这个文件；
- 宿主在每次用配置前（pre-step、时钟 tick）看一眼 mtime，变了就重读，保存后不用重启；
- 「恢复默认」删文件，next 一拍回到 patch 里的 `config`；
- 文件被写坏时保留上一份好配置，等下一次 mtime 变化再读，别让一次手滑把提醒全关掉。

代价是每步多一次 `statSync`，可忽略；换来的是升级插件、改 patch 都不会丢用户设置。

## 为什么直接改 qqbot 的 prefs，而不是调它的接口

想「让这个群换一个新会话」，顺手的做法是调 qqbot 自己的接口。但它**没有暴露**这个能力：

- 群会话的 id 存在进程内存 + `~/.dsh-qqbot/model-prefs.json` 里，插件间没有公开服务能按
  sessionKey 改 sessionId；
- 它自己的 `/new` 命令能把内存与文件一起改、立即换会话，但只在私聊可用，既没法指定新 id，
  也没法只对某一个群操作、同时保留其他绑定。

所以这里直接读写那个 JSON 的一条映射：最小改动、可回滚、不影响 qqbot 其他状态。

**为什么这个按钮不能立即生效**：qqbot 的 `PrefsStore` 在构造时 `load()` 一次，把 `sessionIds`
读进内存 Map，之后既没有 reload 也没有文件 watch；会话恢复只查这个 Map。所以外部改文件后，
正在跑的 qqbot 完全看不到，**必须重启桌面端（托盘退出再打开）**，它启动时重新 `load()`
才会用上新 sessionId。这不是实现偷懒，而是直接改文件这条路的固有代价——如果哪天 qqbot 暴露
了「按 sessionKey 换会话」的公开接口，应该整体改调接口，把这条内存/文件同步交给它自己管。

**代价是耦合**。`model-prefs.json` 是 qqbot 的内部实现，不是契约：

- 它升级后若改了结构或换了存储位置，本插件的列表会变空、换新会失败；
- 写回时必须保留 `overrides` / `presets` / 未知键，否则是在替别人做数据迁移；
- 运行中的 qqbot 已经把旧映射读进内存，所以换新只在重启桌面端后生效。

对应的防线：只改 `sessionIds` 里的那一条、写前备份成 `.bak-<时间戳>`、`.tmp` + rename 原子写回、
失败不清空原文件、每次换新记一行 jsonl 审计。宁可换不成，也不留无法回滚的改动。如果哪天
qqbot 暴露了公开接口，这一段应该整体换掉。

## 已知的笨拙之处

- 时钟行只在进程活着时按间隔写，关机期间的空白补不回来；
- 定时器用 `unref()`，进程要退时不拦着；
- 阈值状态不落盘；
- QQ 群会话换新要重启桌面端才生效，界面只能提示、没法替用户确认新会话已经接上。
