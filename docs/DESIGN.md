# 设计取舍

一页纸，记几个当时想清楚的问题。以后要改它的人（包括几个月后的我）先看这里。

## 为什么不做成改 DSH

插件是 profile 下的独立包，靠 `cordis.patch.yml` 插一行挂上去，DSH 本体和任何 `node_modules` 都不动。卸载 = 删一行 + 删目录。

代价是只能站在公开的接缝上：`agent/pre-step` 事件、`ctx.tokenMeter` 服务。接缝不够用的时候，是收窄需求，不是去 patch 内部。

## 为什么挂在 pre-step 注入

宿主每轮发请求前会走一次 `agent/pre-step`，处理函数能拿到 `decision.messages`，往里追加消息即可让这条内容进入本轮请求。`@deepseek-ai/dsh-time-context` 就是这么做时钟读数的，照抄它的形状：

- 用 `createUserMessage` 构造，`source.kind` 写插件自己的名字，`form: 'snapshot'` 加 `sections`，这样消息在会话日志里可回溯、也能被审计出是谁注的；
- 监听器用 `{ prepend: true }`，排在别的 pre-step 监听器前面。

反面选项是不注入、只提供工具。没选它，是因为工具要我主动想起去调，而水位恰恰是「想不起来看」的时候最需要。

## 为什么读不到就静默

`contextPressure()` 的 `pressureTokens` 和 `contextWindow` 都可能缺：宿主刚起来、这一场还没发过请求、或者换了模型没拿到容量。这时：

- 不注入任何内容（注入一条「水位未知」只会占位置）；
- 不抛错、不写日志刷屏（水位是辅助信息，不该有能力打断会话）。

同样的原则用在时钟写上：写文件失败就吞掉，不让它影响聊天。状态文件（`aux-state.json`）也一样，读不到当没提醒过、写不进就靠进程内计时兜底。

## 为什么四档提醒各说各话、每会话只记一次

四档要求的动作不一样：50% 是「先落盘」，75% 是「要折叠了、细节会丢」，90% 是「这场该收了」，
写长期记忆是「顺手把结论记下来」。合成一句「上下文偏高」就丢了指令性——收到的人不知道该干嘛。
所以每档各有一句自己的文案，文案里的 X 是**当时**的占比。

每档只提醒一次，因为重复提醒会变成噪音，反而让人学会忽略它。内存里按会话记已提醒的档位；插件重启后重计，接受这个不精确。

前三档必须递增：它们是一条阶梯，乱序的输入没法给模型一个稳定预期。但 0 表示「这一档关掉」，不是
阶梯上的点，所以 2.4.0 起只有**大于 0** 的档之间才要求严格递增（`50/0/90` 合法，`0/70/50` 不合法，
`0/0/0` 也合法）。设置页先拦一道，`normalizeSettings` 再排序修正一道——两层都防，是因为设置页可以
被绕过（直接改 JSON），而后端是唯一裁判。第四档（`ledgerPercent`）不在阶梯里，只钳制到 0–100，
可以落在任意位置——理由见下一节。

## 为什么用「百分比填 0」关档，而不是独立开关

因为要关掉提醒的人，几乎都不是「一条提醒都不想要」，而是「只想关掉某一档的打扰」：有人嫌 50% 那条
太早、有人只在折叠前才需要提醒、有人不用长期记忆所以不想看见「落账」那句。一个大总闸只能全开或
全关，逼着人为了少一句噪音把有用的那几条一起关掉。所以粒度必须按档拆开。

但 2.4.0 之前，每一档除了百分比还有自己的布尔开关（`handoverEnabled` / `compactSoonEnabled` /
`nearlyFullEnabled`）。两个旋钮表达同一件事，就一定会出现「开关开着、百分比填了个数，到底响不响」
这种要读代码才知道的组合，面板上也得为每一档并排放一个输入框和一个开关。2.4.0 起改成
**百分比填 0 = 关闭这一档**：

- 一个数字说明白：0 就是关，50 就是 50% 开；
- 少两个开关：2.4.0 一度把三档从「三个布尔 + 三个数字」六项压成三个数字，面板和文档都少一层；
- 少一处不一致：开关与阈值不会再互相打架，`normalizeSettings` 按一种表示兜底。

2.5.0 一度把折叠 / 用完两档的勾做成「发不发这条提醒」（`compactSoonEnabled` /
`nearlyFullEnabled`），与填 0 表达同一件事。2.6.0 纠正了这个理解：**三个勾统一叫「写交接」，
管的是这一档要不要写/更新交接文件，不管提醒发不发**。这样三档的动作终于对齐——提醒是提醒，
落盘是落盘，想静音就把百分比填 0，想不落盘就取消勾，两个诉求各有一个入口，不互相冒充。
交接档的勾本来就是这个语义，现在三档一致了。

代价是「勾」不再是一键静音：要静音还是得把百分比改成 0（会丢掉原水位值）。这是刻意的：
2.5.0 那版让勾与 0 表达同一件事，反而制造了「勾没勾、百分比还开着，到底响不响」的组合歧义。

代价还有 0 不再是阈值（不存在「到 0% 才提醒」的档），递增规则也得改成**只有大于 0 的档之间
才比较**。这两点都写进了 `lib/settings.js` 的注释、面板小字与 README，不靠记忆。

### 为什么后两档是「更新同一份文件」，而不是各起一份

交接文件的意义是「下一次开工先读这一份」。如果 50% / 70% / 90% 各落一份，下次开工面对的
就是三份名字几乎一样的文件，还得先判断哪份最新、哪份是最终态——这比没有交接更费神。
同一天、同一场只该有**一份**交接，所以：50% 首次写（文件已存在就不动，跨线重复不重复写），
70% / 90% 各往同一份文件末尾**追加**一段带时刻的更新块（`## 更新 · <档位>%（HH:mm）`）。
更新块只留标题和空位，内容由助手填——插件不知道这一场做了什么，也不该假装知道。

这样文件本身就是一条时间线：开头是骨架，越往下越接近这一场的终态。跨会话、跨重启都在，
而且不需要额外记录「这次写到第几段」。

### 为什么「写长期记忆」要拆成独立一档

2.4.0 里它挂在交接档上（`ledgerReminderEnabled`），只在交接提醒末尾追加一句。问题在于
**它和交接要的动作不一样、合适的水位也不一样**：交接是「这一场快该收了，先把结论落盘」，
通常发生在 50% 前后；落账是「顺手把结论存进长期记忆」，可以再晚一点，等这一场真的攒够内容
（比如 70%）再说。绑在交接上就只能跟着 50% 一起响，要么太早（没什么可落），要么为了等落账
把交接整体推后。

拆成 `ledgerPercent` 独立档后，两者各配各的水位：交接 50、落账 70 是合法组合；
落账也可以提前到交接之前。代价是多一项配置、面板多一行——但它本来就不是交接的副作用，
硬绑在一起只会逼用户二选一。

独立档还有两个直接好处：
- **不参与递增**：它不是「上下文越高越紧急」的同一类提醒，只钳制到 0–100，可以和任何一档相等；
- **关起来不牵连别人**：不想看见落账那句就把 `ledgerPercent` 填 0，交接的提醒与交接文件照常。

## 为什么交接文件落成文件，而不是塞进注入

三档提醒里，handover 那一档最「该动手」：它要求把这一场的结论落盘。顺手就能再往前一步——
直接给一份填好骨架的交接文件，省掉「新建、抄格式、想起要写哪几段」这三步。但**模板正文不进注入**。

原因只有一个：注入是**每一轮都在上下文里的东西**。把一份几百字的模板塞进去，等于从跨过 50%
那一刻起，每轮都多烧几百 token，而模板只在真正写交接时才需要看一次。所以注入里只留一行指针
（`模板已生成：<绝对路径>` / `交接已存在：<绝对路径>` / `交接已更新：<绝对路径>`），需要时按路径
去读——文件是给下一次开工读的，不是给当前上下文看的。这一行是纯收益：比「记得去写交接」多一个
具体位置，比贴全文省下每轮的上下文。

落成文件的另外两个好处：模板本身就是「下次开工先读」的载体（写完的几段留在磁盘上，跨会话、
跨重启都还在，不吃上下文）；而且它可被别的脚本、编辑器、git 直接消费，不必经过对话。

文件名里带日期和会话短 id，是为了同一天多个会话各落各的、互不覆盖。**同一份文件内**则由三档
接力：交接档只在不存在时放骨架（已存在就不动，因为文件一旦被填过就是人的成果），折叠 / 用完
两档只往末尾追加更新块——这是「同一天同一场只有一份交接」的直接结果（理由见上一节）。写失败
一律吞掉，理由和时钟行、状态文件一致：辅助产物不该有能力打断会话。

## 为什么累计和百分比分开看

百分比是当前窗口占用，折叠之后会回落；累计 token 只增不减。拿累计反推百分比在折叠前勉强成立，折叠后必然失真。

所以：**该不该换新会话看累计**（那是总账），**离下次压缩还有多远看百分比**（那个由宿主自己管）。插件只负责把百分比送到模型眼前，不试图把两个概念缝成一个。

## 时钟行为什么要带百分比

同一行里既有真实时间又有当时的水位，事后回看能对上「几点开始变慢」这类问题。多写几个字符，省一次交叉比对。

## 为什么设置和状态分两个文件

`cordis.patch.yml` 是用户 profile 的东西，里面还有别的插件的行、注释和 `!!js` 表达式。
插件不该为了存自己的开关去重写它。所以：

- 设置页把值写到 `%USERPROFILE%\.dsh\aux-settings.json`，只碰自己这个文件；
- 宿主在每次用配置前（pre-step、时钟 tick）看一眼 mtime，变了就重读，保存后不用重启；
- 「恢复默认」删文件，下一拍回到 patch 里的 `config`；
- 文件被写坏时保留上一份好配置，等下一次 mtime 变化再读，别让一次手滑把提醒全关掉。

状态（`%USERPROFILE%\.dsh\aux-state.json`，只记 `lastRotateReminderAt`）单独一个文件：
它不是用户设置，不该出现在设置页、也不该被「恢复默认」清掉。代价是每步多一次 `statSync`，可忽略；
换来的是升级插件、改 patch 都不会丢用户设置。

## 为什么换新改成外置脚本，插件只负责按时提醒

原来插件自己在设置页里改 qqbot 的 `model-prefs.json`：列绑定、铸新 session id、备份、原子写回。这让它变成

- **跨插件耦合**：直接依赖 qqbot 的私有 JSON 结构，对方一升级就可能列不出、改不动；
- **一个必须重启才生效的按钮**：qqbot 只在构造时读一次文件，缓存进内存 Map，外改不会热加载；
- **权限面放大**：为了换会话，一个只管「读数 + 提醒」的插件要去写别的进程的状态文件。

现在的分工是：**插件只按时提醒，换新交给外置脚本 `tools/rotate-qq-session.mjs`**（先写交接，再改绑定，
最后重启）。插件因此**不碰别人的存储**：不读 `model-prefs.json`、不缓存绑定、不铸 session id、
不写审计日志。对应的 HTTP 接口（`/api/aux/bindings`、`/api/aux/rotate`、`/api/aux/rotations`）
和 `lib/bindings.js` 一并删掉，备份/回滚那些防线挪到脚本那边自己管。

代价是提醒和动作之间多了一步人工：插件说「该换了」，真正换要跑脚本。但这一步本来就该有人确认
（换不换、什么时候换是你定），插件不越权替你做，也不再因为读别人的文件而在升级时一起坏掉。

## 换新提醒为什么是「三选一」而不是一个天数

一开始只有「每 N 天」。但真实用法分得很清：有人按周记（周末统一收尾），有人按月记（月初换），
也有人就是「用了三天就换」。只给天数，按周的人得自己算 7 天会不会漂；只给星期几，又不够灵活。
所以做成三选一模式，各自一个输入，互不干扰：

- `interval`：纯间隔，简单直接；
- `weekly`：日历上最近的那个星期几，跨月也不会漂；
- `monthly`：每月固定几号，日期上限取 28，保证每个月都有这一天。

「周几 / 几号」一律用配置的 `timeZone` 算本地日期，不是 UTC——不然东八区的「周六」会从周五晚上
开始算，提醒就提前一天。到期判断抽在 `lib/rotate-schedule.js` 的纯函数里，单独可测，不用起宿主。

提醒还做两件事，各有各的用途：**注入对话**（让模型知道该收尾了）和**在时钟文件里留一行**
（`YYYY-MM-DD HH:mm · 该换会话`，让人事后翻时钟时看到「那天提醒过换会话」）。这一行跟按
`clockIntervalHours` 写的常规时钟行分开写、互不覆盖，也不去重——它们是两种记录，混在一起才难读。

提醒本身也可以按会话收窄（`scopeSessions`，见下一节）；为什么做成全局而不是每项一个开关，那节里写。

## 为什么生效范围是全局的，而不是每项一个开关

`scopeSessions` 是一刀切：非空时只有会话 id 等于某一项、或以某一项前缀开头的会话才收到**任何注入**
（读数、三档提醒、换新提醒），空数组就是所有会话。没给每项注入各配一个范围，是因为那样同一个范围
要填好几遍：

- 需要限定范围的场合几乎都是「这条规则只对这个会话有意义」（某个专用工作会话、某个群），这些注入
  本来就会一起出现或一起不出现；
- 每个注入项各配一个范围（那就是四个范围开关）意味着面板上多几行输入、设置文件和文档多几个键，
  还多出「读数在这个会话、提醒在另一个会话」这种没人想要、却要花力气解释的组合；
- 判定点只剩一个：`lib/settings.js` 的 `inScope()` 一处纯函数，pre-step 里一处 early return，
  不会出现「范围外的会话把读数门限、已提醒档位、换新提醒状态推着走」这类问题。

前缀匹配而不是正则，是为了让配置能手写、能一眼看懂（只填 `session-3df4e987` 就够了）。代价是粒度粗：
想要「三档提醒开、换新提醒关」这种组合，现在只能靠 `injectPerTurn` 单独关读数；真出现需求再加开关，
而不是先摊成四份。

## 已知的笨拙之处

- 时钟行只在进程活着时按间隔写，关机期间的空白补不回来；
- 定时器用 `unref()`，进程要退时不拦着；
- 四档提醒状态不落盘（只有换新提醒的状态落盘）；
- 状态里只记「上次提醒时间」，所以改了模式或星期几之后，下一次到期点会按新配置从上次提醒时间重算；
- 换新提醒的会话范围（现在叫生效范围 `scopeSessions`）只认字符串前缀，写错前缀那个会话就静默不注入
  （留空最稳）；而且它是全局的。要「按类关掉」只能靠四档百分比填 0，或者取消三档各自的「写交接」勾
  （勾只停写文件，不停提醒；读数、四档提醒各有一个入口），**换新提醒本身没有独立开关**，只能靠
  会话范围把它挡在某几个会话之外。
